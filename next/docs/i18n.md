# Internationalization (i18n)

This document describes the i18n system for the Tidex application.

## Overview

The app supports multiple languages with cookie-based locale persistence and automatic detection from browser preferences. The system follows Next.js 16 patterns with:

- Server-side locale detection in middleware ([proxy.ts](../proxy.ts))
- Cookie-based persistence
- Server and client translation utilities
- Type-safe dictionary structure

## Supported Locales

- `no` - Norwegian (Bokmål) - Default
- `en` - English

## Architecture

### Locale Detection Flow

1. **Initial Visit**: [proxy.ts](../proxy.ts) checks for locale cookie
   - If no cookie exists: Detect from `Accept-Language` header
   - Set `tidex-locale` cookie with detected or default locale

2. **Subsequent Visits**: Cookie value is used directly

3. **Manual Switch**: User clicks language switcher
   - Client calls `/api/locale` endpoint
   - Cookie is updated
   - Page refreshes with new locale

### File Structure

```
lib/i18n/
├── config.ts              # Locale configuration and constants
├── dictionaries/
│   ├── index.ts          # Dictionary loader
│   ├── no.ts             # Norwegian translations (source of truth for types)
│   └── en.ts             # English translations
├── server.ts             # Server-side utilities
├── client.ts             # Client-side utilities
└── index.ts              # Public exports

components/
├── providers/
│   └── I18nProvider.tsx  # Context provider for client components
└── app/
    └── LanguageSwitcher.tsx  # Language switcher UI

app/
├── layout.tsx            # Root layout with I18nProvider
└── api/locale/
    └── route.ts          # Locale update endpoint
```

## Usage

### In Server Components

```tsx
import { getTranslations } from '@/lib/i18n';

export default async function MyPage() {
  const t = await getTranslations();

  return <h1>{t.common.loading}</h1>;
}
```

### In Client Components

```tsx
'use client';

import { useTranslations } from '@/lib/i18n';

export function MyComponent() {
  const { t, locale } = useTranslations();

  return <button>{t.common.save}</button>;
}
```

### Language Switcher

```tsx
import { LanguageSwitcher } from '@/components/app/LanguageSwitcher';

export function Header() {
  return (
    <header>
      <LanguageSwitcher />
    </header>
  );
}
```

## Adding Translations

### 1. Add to Norwegian dictionary first

Edit [lib/i18n/dictionaries/no.ts](../lib/i18n/dictionaries/no.ts):

```typescript
export const no = {
  common: {
    // ... existing keys
  },
  shifts: {
    title: 'Skift',
    addNew: 'Legg til nytt skift',
    // ... more keys
  },
} as const;
```

### 2. Add matching keys to English dictionary

Edit [lib/i18n/dictionaries/en.ts](../lib/i18n/dictionaries/en.ts):

```typescript
export const en: Dictionary = {
  common: {
    // ... existing keys
  },
  shifts: {
    title: 'Shifts',
    addNew: 'Add new shift',
    // ... more keys
  },
} as const;
```

**Important**: The Norwegian dictionary (`no.ts`) is the source of truth for TypeScript types. English and other locales must match its structure exactly.

## Type Safety

All translations are fully typed. If you add a key to Norwegian but forget it in English, TypeScript will error:

```typescript
// ✅ Correct - both have the same keys
no.common.save
en.common.save

// ❌ Error - missing in English
no.common.newKey  // exists
en.common.newKey  // Type error!
```

## Locale Detection Logic

The [proxy.ts](../proxy.ts) middleware handles automatic locale detection:

```typescript
function detectLocaleFromHeader(request: NextRequest): Locale {
  const acceptLanguage = request.headers.get('accept-language');
  // Parses header like "en-US,en;q=0.9,no;q=0.8"
  // Returns first matching supported locale or default
}
```

Quality values (q-values) are respected when determining the best match.

## Best Practices

1. **Always add to Norwegian first** - It's the type source
2. **Use semantic key names** - `shifts.addNew` not `shifts.button1`
3. **Group related keys** - Use sections like `common`, `shifts`, `auth`
4. **Keep translations short** - Consider mobile UI constraints
5. **Avoid HTML in translations** - Use composition instead:

```tsx
// ❌ Bad
const t = { message: '<strong>Hello</strong> world' }

// ✅ Good
const t = { greeting: 'Hello', message: 'world' }
<p><strong>{t.greeting}</strong> {t.message}</p>
```

## Migration Guide

When extracting hardcoded text to translations:

1. Identify the text and its context (e.g., "Save" button in shift form)
2. Add to `no.ts` under appropriate section
3. Add English equivalent to `en.ts`
4. Replace hardcoded text with `t.section.key`
5. Update component to use `useTranslations()` (client) or `getTranslations()` (server)

Example:

```tsx
// Before
export function SaveButton() {
  return <button>Lagre</button>;
}

// After
'use client';
import { useTranslations } from '@/lib/i18n';

export function SaveButton() {
  const { t } = useTranslations();
  return <button>{t.common.save}</button>;
}
```

## Testing Locale Switching

1. Open browser DevTools > Network
2. Click language switcher
3. Verify POST to `/api/locale` succeeds
4. Check Application > Cookies for `tidex-locale`
5. Refresh page - should maintain selected locale
